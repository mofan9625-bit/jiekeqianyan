> ⚡ **专栏前言**：Vol.1 我们拆过 ChatGPT 的全能与幻觉，今天轮到另一位“长文本与代码美学”的代表选手——Claude 3.5 Sonnet。它经常被形容成更像人类编辑的模型，但真正上手后，你会发现它既能把一份混乱需求整理成漂亮方案，也可能用很自信的语气把一个不存在的 API 写进项目。本文不看宣传页，只讨论它在真实工作流里值不值得留下。

【核心定位】一句话看懂 Claude 3.5 Sonnet

Claude 3.5 Sonnet 的优势不在“什么都能做一点”，而在于能稳定处理长上下文、复杂指令和需要反复修改的文本。把几十页产品需求、旧代码和会议纪要一起交给它，它通常能先建立结构，再给出修改建议；面对一段已有代码，它也更愿意解释设计取舍，而不是直接推倒重写。它适合做副驾驶，不适合做无需验收的自动驾驶。

【红榜：真正能省时间的地方】

1. 长文档分析，结构感很强

把一份 8 万字的访谈稿交给 Claude，让它提取用户痛点、按角色聚类，再输出一页产品路线图，通常比“逐段总结”更自然。它会主动识别重复观点，保留冲突意见，并指出哪些结论缺少原始证据。写作时也可以先给它一份提纲和语气样本，让它只扩写论据、不改变章节顺序，返工次数明显少于普通套壳写作工具。

2. 代码重构与解释，适合接手旧项目

Claude 的代码回答常常不追求炫技，而是先说明风险：哪些函数耦合过高、测试应该覆盖什么边界。给它报错堆栈和相关文件，它能按“原因—最小修复—回归测试”的顺序推进。对前端组件、正则表达式和 SQL 查询尤其顺手，适合把旧代码整理成团队看得懂的版本。

3. 文案润色不油腻，能守住人设

它很擅长根据参考文本提炼语气规则。给三篇品牌推文，再要求写一封售后邮件，它通常能避开夸张营销词，保留品牌的克制感。明确“不允许什么”，成稿会更稳定。

【黑榜：看起来聪明，实际容易翻车】

1. 代码幻觉更隐蔽

Claude 生成的代码往往格式漂亮、注释完整，因此错误更难被第一眼发现。它可能把旧版本 SDK 的方法名混入新项目，或者默认某个库支持并不存在的参数。解决办法不是反复追问“你确定吗”，而是要求它先列出依赖版本，再生成最小可运行示例，并用本地测试结果逐条回填。没有编译、单测或接口文档的验证，任何代码都只能算草稿。

2. 长上下文不等于永远记得

把所有资料一次性塞进去，会让模型抓住大量背景，却忽略真正的问题。尤其在长对话后半段，它可能把早期的临时假设当成最终规则。建议每完成一个阶段就让它输出“当前共识、未决问题、下一步输入”，下一轮只携带这份摘要和必要原文，准确率反而更高。

3. 联网、额度与地区可用性会打断心流

Claude 的能力上限很高，但不同入口的联网、文件处理和消息额度并不一致。高峰期遇到限流时，正在进行的长任务可能被迫中断；部分第三方客户端还会偷偷更换模型。订阅前先确认官方入口、账单周期和数据保留政策，不要把公司机密直接粘贴进来，也不要为“无限额度”这种模糊承诺付费。

4. 中文表达仍需人工定稿

它能写出通顺中文，却不一定理解本地语境里的分寸。涉及法律、医疗、行业黑话或品牌禁用词时，偶尔会出现“字面正确、语用不对”的句子。让它先做事实层和结构层，再由熟悉业务的人做最后一遍语气审校，效果最好。

【实测工作流：把 Sonnet 放在正确的位置】

这套流程可以概括为：资料输入，模型抽取结构；人工确认事实；模型生成方案；本地测试后再发布。每一步都留下可回滚记录，问题才容易定位。

我的推荐顺序是：先让 Claude 做“分析员”，再让它做“执行者”。第一轮只提问、归纳和标注不确定性；第二轮才生成文案或代码；最后贴回测试结果，让它解释失败原因。这样能利用长上下文，也能把幻觉限制在可回滚的草稿阶段。需要实时资料时，先用 Perplexity 或搜索工具核验来源，再交给 Claude 整理。

【最终结论：值得订阅，但别交出方向盘】

如果你的工作包含长文档、旧代码、复杂改稿，Claude 3.5 Sonnet 是红榜选手；如果你只想问几个常识问题，免费聊天工具已经够用。它最强的地方是耐心、结构和修改能力，最危险的地方则是错误往往披着专业外衣。把它当成一位速度很快、需要同行评审的资深助理，你会得到生产力；把它当成事实裁判，你迟早会被它的自信反噬。
